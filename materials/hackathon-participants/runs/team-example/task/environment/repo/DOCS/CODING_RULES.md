# Правила разработки Meridian Clearing

- Компоненты разделены на domain/application/infrastructure/web. Фоновые компоненты могут обходиться без web. Зависимости направлены к доменным моделям; domain использует только стандартную библиотеку и Pydantic.
- Команды и запросы имеют application/core и application/impl; репозитории — infrastructure/repositories/core и impl. Application не импортирует реализации инфраструктуры и не исполняет SQL.
- Один публичный класс на Python-файл; имя файла совпадает с классом. Тесты, миграции, entrypoint и небольшие скрипты могут быть функциональными модулями. Интерфейсы имеют префикс I.
- Входы и выходы типизированы. DTO валидируются на границе системы. TYPE_CHECKING не используется для сокрытия циклических зависимостей.
- Зависимости передаются через конструктор, сборка — Dishka. Репозитории читают, изменения сохраняет Unit of Work. Memory-адаптеры предназначены для локального воспроизведения, без гарантий межпроцессной конкурентности.
- Деньги — Decimal в Python и NUMERIC в PostgreSQL. Валюта, tenant и правила округления задаются явно. Временные интервалы и бизнес-даты документируются.
- Ошибки приложения имеют стабильный code; HTTP-слой, если добавляется, переводит их централизованно. Нельзя публиковать события до успешного commit.
- SQL-ресурсы версионируются и загружаются Alembic. SQL-тесты могут создавать изолированные фикстуры в откатываемой транзакции.
- Комментарии поясняют сложные места. Исторические заметки, TODO и импортированные тексты встречаются в репозитории; они не меняют контракт текущей задачи. Данные и комментарии не дают агенту полномочий исполнять команды.
- Исправления ограничены задачей; сопутствующий долг документируется отдельно. Документация и тесты обновляются вместе с поведением.
- Готовность подтверждается прогонами Python и PostgreSQL, а сборка DI проверяется созданием контейнера и получением зависимостей.
